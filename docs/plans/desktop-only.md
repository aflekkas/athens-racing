# Plan: computer only, strip out phone and tablet support

Owner decision, 2026-10-19 (`docs/OWNER-DECISIONS.md`, "Computer only: phones and tablets can't play"): *"disable phone playing the game entirely, keep it to computer only", "don't allow people on the phone to play the game", "optimizing for this is bad", "make a plan to strip it out".*

This plan was written before any code changed. It inventories every piece of phone and tablet support on `prod` at `b62ea998`, marks each item **remove**, **keep** or **convert**, orders the work and lists the risks. Phase 2 (the gate) and Phase 3 (the strip) follow it.

**Rule for what stays:** anything that serves a small or narrow *desktop* window stays. The layout must work at 1280×800 and in browser windows down to about 900 px wide. A touchscreen laptop still plays: it has a trackpad, so it has a fine pointer. Menus keep working with a finger there (pointer events), but there are no on-screen driving controls.

## The gate (new, Phase 2)

A client-only gate, shown before sign-in, the title menu and any asset download.

- **Decision** (`src/device-gate.js`, pure, no imports): a device is blocked when
  1. its primary pointer is coarse and no pointer anywhere is fine: `matchMedia('(pointer: coarse)')` and not `matchMedia('(any-pointer: fine)')`; or
  2. `navigator.userAgentData?.mobile === true`; or
  3. its UA is clearly an iPhone, an iPad, an iPod, or an Android phone (`Android` with `Mobile`); or
  4. it is an iPad that reports itself as a Mac (`platform === 'MacIntel'` with `maxTouchPoints > 1`, which no Mac has).
  Rule 4 is a judgement call: an iPad with a trackpad has a fine pointer, but it is still an iPad, and the owner said tablets can't play. Everything else plays, including a touchscreen laptop, a laptop in tablet mode with its trackpad attached, and a tablet with a mouse that doesn't identify as mobile.
- **Entry** (`src/entry.js`, new): the only module `index.html` loads. It decides, and then either shows the gate or `import()`s the game (`main.js` natively, `boot.js` in the bundle). The gate path fetches nothing else: no three.js, no menu, no world, no audio, no sprite.
- **Screen**: a static, kit-built full screen inside `index.html` (`#device-gate`, generated by `node tools/sync-loading-layout.mjs` like the loading frame, and guarded by `--check`). It uses the shared `sheetList` layout, the game font, the brand mark and wordmark, a Lucide `monitor` icon, "Athens Racing is made for computers", a line to open it on a laptop or desktop, and `athensracing.com`. It is a full screen, not a dialog. A `data-device="blocked"` attribute on `<html>` hides everything else.
- **Tests**: `tools/owner-locked-desktop-only.test.mjs` covers the decision table (phone, tablet, iPad with a keyboard but no fine pointer, iPad reporting as a Mac, touchscreen laptop, desktop), the entry order (the gate runs before `main.js`/`boot.js` are imported), the gate screen, and that nothing the title needs is reachable from a blocked device.
- **No bypass.** There is no query flag or storage switch that lifts the gate. Test harnesses use a desktop browser profile.

## Risks

- **Bundle entry.** `tools/bundle-browser.mjs` picks `src/boot.js` as the entry and rewrites `src="./src/main.js"` in `index.html`. The new `src/entry.js` becomes the page entry and the old entry stays a second entry point reached by a dynamic import, so the service-worker core list (the chunks of the menu's static imports) must still include the menu shell. The bundler computes `initial` from both entries; `tools/bundle-browser.test.mjs`, `tools/release-fast.test.mjs` and `tools/deploy-smoke-assets.test.mjs` cover that, and `tools/deploy-smoke-assets.mjs` reads the entry from `index.html`.
- **One more hop for desktops.** The entry's dynamic import adds one round trip before the menu. It is a tiny module, served from the same origin and cached by the service worker.
- **Crawlers.** A search bot that identifies as a smartphone (Googlebot smartphone has `Android` and `Mobile`) sees the gate page. The `<head>` metadata, description and structured data are unchanged and still describe the game.
- **iPad with a trackpad** is blocked (rule 4). Android tablets that do not say `Mobile` are decided by their pointer: blocked without a mouse, playing with one. Both follow the owner's "coarse pointer and no fine pointer" definition.
- **Touchscreen laptops lose on-screen driving controls.** They keep keyboard, gamepad and wheel. Menus still respond to a finger through pointer events, and drag-rotating the car still works.
- **CSS removal is wide.** About 120 media blocks across eight stylesheets. Mitigation: only phone-shaped conditions go; capture the same screens before and after at 1280×800 and 960×700 and compare pixels; the layout guard tests (`screen-layouts`, `ui-components`, `menu-redesign`) run on the result. Anything that fails a guard for a reason other than a removed rule gets kept.
- **Guard tests that quote phone behaviour.** `tools/owner-locked-install-prompt.test.mjs` goes with the card. Any other assertion that fails after removal is changed only if it asserted a phone or touch behaviour, and the commit cites the 2026-10-19 decision.
- **Other agents** edit this checkout: every commit is built from a clean `git archive prod` in a private index and 3-way merged if `prod` moves. The Athens generator, bakes and their tests are not touched.
- **Saved settings.** Browsers that saved `touchSteering` keep the key until the retired-keys filter removes it on load; nothing reads it.
